# E2E Scenario Matrix Skill

Every user-visible behaviour of **Historic City Map Maker** has at least one **happy** and one **bad** scenario, registered in `e2e/scenarios.json` before the behaviour counts as done. The registry was seeded from `docs/research/design-review-testability.md` §4.5 (viewer V01–V18, admin A01–A21, pipeline P01–P02) plus the consent and crash-reporting behaviours of `docs/research/PLAN.md` → *Addendum 2* (V19, V20, A22) and the M1 contracts of `docs/research/M1-interfaces.md` §9 (the embed API V21, and rows for engine compatibility, the legacy hash, markup in About, a photo without bearing and a mismatched `cityId`), plus PLAN Addendum 3: live overlay opacity (V22), overlay opacity in the URL hash (V23, which took over the two `op=` rows of V05) and points of interest (V24), served from the e2e fixture manifest of `docs/research/M1-interfaces.md` §10; and the M2 backend contracts of `docs/research/M2-interfaces.md` §6 (refined A01–A07, A20 and A22 rows, edit history and revert A23, the crash reporting endpoint A24); and the M2b admin contracts of `docs/research/M2b-interfaces.md` §5 (refined A04, A07 and A22 rows; bootstrap mode before Blaze A25, deployment detection and the automatic owner claim A26, Google OAuth scopes A27, the legacy Bucharest import A28, navigation and layout A29, minimum admin input A30); and the M2c editor contracts of `docs/research/M2c-interfaces.md` §12.1 (refined A02, A08–A10, A14, A16, A18–A23, A29–A31; POI drawing A32, delete with confirmation and Undo A33, POI GeoJSON import and export A34, layer image adjustments A35, overlay default opacity A36, photo replace A37, editor drafts and saving A38, POI categories A39).

This file holds the rules; it never states test counts. Counts appear only in the `## Counts` section of `docs/E2E_SCENARIOS.md`, generated from the registry by `python3 scripts/ci/check_e2e_matrix.py write`.

## Registry format

`e2e/scenarios.json` is one object. `scenarios` is the list the `e2e-matrix` gate checks; `behaviours` names each behaviour id with its area, milestone and source (documentation for people and agents; the gate ignores it).

```json
{
    "id": "S-V01-BAD-MANIFEST404",
    "behaviour": "V01",
    "area": "viewer",
    "path": "bad",
    "title": "Manifest 404 shows a localized error with Retry",
    "asserts": "manifest 404 -> localized error message and a Retry button",
    "tier": "e2e-viewer",
    "status": "planned",
    "notes": "Milestone M1."
}
```

| Field | Meaning |
| --- | --- |
| `id` | `S-<behaviour>-HAPPY` for the happy row (`S-<behaviour>-HAPPY-<SLUG>` when a behaviour has more than one), `S-<behaviour>-BAD-<SLUG>` for each bad case; upper case letters, digits and dashes |
| `behaviour` | `V01`…, `A01`…, `P01`…; one behaviour stays in one area |
| `area` | `viewer`, `admin`, `starter-kit`, `pipeline`, `functions` or `rules` |
| `path` | `happy` or `bad` |
| `title` | the test title |
| `asserts` | what the user sees when it passes; never "no crash" |
| `tier` | `e2e-viewer`, `e2e-admin`, `e2e-starter-kit`, `e2e-pipeline`, `functions` or `rules` (no `unit`: a UI or shared behaviour proved by unit tests only is an `e2e-admin` or `e2e-viewer` row with status `planned` and the unit test named in `notes`, M28 2026-11-14) |
| `status` | `planned` until a test names the id, then `exists` |
| `notes` | optional: the milestone that delivers it, caveats |

Any other row field fails the gate. The allowed values are the tuples in `scripts/ci/check_e2e_matrix.py` (`AREAS`, `TIERS`).

## Rules

1. A behaviour change edits its rows and its tests in the same task. A new behaviour gets a new id (and an entry in `behaviours`) with at least one happy and one bad row.
2. A test names its scenarios: Playwright with `{ tag: '@S-...' }`, a Vitest test of `functions/test/`, `firebase/rules-tests/`, `packages/admin/test/georef/` or `packages/shared/test/georef/` with `@S-...` in its title (the gate matches the tag anywhere in a test file; in an `it.each`, put it in the case's name), pytest with a docstring line `Scenarios: S-..., S-...` (matched only at the start of a line; keep only ids on that line). A row and the tags that name it land in the same change: the gate refuses a tag on an unknown or `planned` row, and an `exists` row without a tag. Test files are searched under `e2e/`, `pipeline/tests/`, `functions/test/`, `firebase/rules-tests/`, `packages/admin/test/georef/` and `packages/shared/test/georef/`.
3. The `e2e-matrix` gate (`python3 scripts/ci/check_e2e_matrix.py check`) works in both directions: every named id is registered, every `exists` row is named by a test, no `planned` row is (flip it to `exists`), ids are unique, every behaviour has a happy and a bad row, and `docs/E2E_SCENARIOS.md` is current. After any registry or tag change run `python3 scripts/ci/check_e2e_matrix.py write` in the image and commit the regenerated doc.
4. A new behaviour takes the next free id in `behaviours`, whatever a brief called it (Addendum 3's V21–V23 became V22–V24 because V21 already existed; the M2 brief's A22 history and A23 crash endpoint became A23 and A24 because A22 was the analytics card; the M2b brief's bootstrap, OAuth, import and input-budget behaviours became A25–A30; the M2c brief's became A32–A39); say so in the task's notes. While several agents work at once, each owns the rows of its own behaviours (`docs/research/M2c-interfaces.md` §11.2): it flips its rows in place and adds a new row right after its behaviour's last one, never touching another area's rows.
5. Assert what the user sees (text, ARIA, a pixel probe, a recorded request); drive the app from outside; mock only external boundaries (Mapbox, USGS, STAC, Nominatim, AI, the network), never an owned module; no network, no sleeps, no wall clock. Use web-first assertions (`toHaveCount`, `toContainText`, `expect.poll`): `count()`, `allTextContents()` or `getAttribute()` inside a plain `expect` reads once and races the render after `hcm-ready`. Poll for the whole state the assertion names: a poll that the previous state already satisfies (markers that contain one id) passes before the change is drawn (`docs/LESSONS.md` 128). A probe a poll calls returns a "not yet" value while the page is still getting there, never throws: a callback that throws ends the poll at once (the admin map's `getStyle()` throws while its style loads; `docs/LESSONS.md` 183). Before leaving an editor after Save, wait for the page's own "Saved", not for the write in the emulator (lessons 122, 131). A snackbar's message is asserted without its live region, which repeats the text a moment later: `getByText(…).and(page.locator(':not([aria-live])'))` (lesson 441).
6. Format the registry with Prettier (4 spaces) and keep every row on the schema above. Titles and `asserts` are copied verbatim into the Markdown tables of `docs/E2E_SCENARIOS.md`: describe markup in words (no raw `<tag>`), or markdownlint rejects the generated doc.
7. A bug a scenario found goes into `docs/LESSONS.md` with the row id that now pins it.
8. The tour tier checks layout, axe and ARIA snapshots on every screen and state; it backs V15, V18 and A21 but does not replace their functional rows.
9. A state the e2e world seems unable to reach is usually a request held or failed at the network: an upload never answered (S-A61-BAD-UPLOAD-HOLDS-RELOAD), a count's `runAggregationQuery` held for the ellipsis or dropped for the dash (S-A40-BAD-COUNT-UNREAD-SHOWN). One `page.route` handler with a mode the test switches; never `page.unroute` while requests are held (`docs/LESSONS.md` 477).
10. Specs are linted with `eslint-plugin-playwright`'s recommended rules (`eslint.config.js`): no sleeps, no `networkidle`, no forced clicks, web-first assertions (`toHaveCount`, `toHaveText` instead of reading `count()` or `allInnerTexts()`), no conditional in a test body and no conditional `expect`. A branch on the window class goes into a helper (`isDocked`, `closeModalSheet`, `manifestIssues` in `e2e/support/viewer.ts`, or a local `expect…` helper), assertion helpers are named `expect…` so `playwright/expect-expect` counts them, and a test function stays within 120 lines: a long journey is one function per step (`e2e/admin/specs/journey.spec.ts`).

## Tiers and projects (M1)

The projects are built by `e2e/projects.ts` and chosen with `E2E_TIER` (comma-separated tiers; unset runs every push's tiers, every one but `tour-matrix`, and so every scenario row; `all` adds `tour-matrix`). Every project runs Chromium under SwiftShader behind the host-resolver rules and depends on `setup` (`e2e/setup/fixture.setup.ts`: the fixture manifest validates, both servers answer, the built site serves the fixture).

Run order is the order of `e2e/projects.ts`: `admin`, `smoke`, `a11y`, `nogl`, `tour` (largest frames first), `tour-matrix`, `fn`. Playwright queues projects in that order and an `E2E_SHARD` slice (`index/total`, or `first-last/total` for a machine that takes more, `scripts/ci/e2e-split.sh`) is a contiguous part of the queue (in a split run, `E2E_ADMIN_PART` gives each machine its part of the admin projects and the slice counts the other tiers only: `e2e/split.ts`, `e2e/split-reporter.ts`): the admin tests start first and run one at a time beside everything else, the long tour tests start early, and the many short functional tests fill the workers to the end. A new tier takes its place in that order by its test length.
